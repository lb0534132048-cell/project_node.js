למה CRUD שונה ממה שעשית עד עכשיו?
עד כה ב-server.js השרת שלך כנראה עשה דברים בסיסיים — לקבל בקשה ולהחזיר תשובה. למשל: לבקש עמוד HTML, או לשלוח JSON קבוע.

CRUD זה כבר לא "לקרוא נתון קבוע" — זה לנהל נתונים דינמיים. הנתונים משתנים בזמן אמת לפי מה שהמשתמש עושה.

ההבדל המהותי: עבודה עם נתונים
בלי CRUD:

bash
העתק קוד
בקשה:  GET /hello
תשובה: "Hello World"  ← תמיד אותו דבר
עם CRUD:

bash
העתק קוד
בקשה:  POST /students  { "name": "יעקב", "grade": 95 }
תשובה: { "id": 1, "name": "יעקב", "grade": 95 }  ← נוצר משהו חדש

בקשה:  GET /students
תשובה: [כל התלמידים שנוצרו עד עכשיו]  ← משתנה כל פעם

בקשה:  DELETE /students/1
תשובה: התלמיד נמחק  ← הנתונים השתנו
מה צריך בשביל CRUD?
1. אחסון נתונים (Data Store)
צריך מקום לשמור בו את הנתונים. יש שלוש רמות:

רמה	דוגמה	מתי
זיכרון (מערך/אובייקט)	let students = []	לבדיקות, הנתונים נמחקים כשהשרת נכבה
קובץ JSON	fs.writeFile	פרויקט קטן, נתונים נשמרים בין הפעלות
בסיס נתונים	MongoDB, PostgreSQL	אפליקציה אמיתית
בשיעור כנראה תתחילו עם מערך בזיכרון.

2. ניתוב (Routing)
כל פעולה צריכה route משלה:

javascript
העתק קוד
// Create
app.post('/students', (req, res) => { ... })

// Read (כולם)
app.get('/students', (req, res) => { ... })

// Read (אחד)
app.get('/students/:id', (req, res) => { ... })

// Update
app.put('/students/:id', (req, res) => { ... })

// Delete
app.delete('/students/:id', (req, res) => { ... })
3. פרמטרים
req.body — הנתונים שהמשתמש שולח (ב-POST ו-PUT)
req.params.id — המזהה מה-URL (ב-GET יחיד, PUT, DELETE)
res.json() — להחזיר תשובה בפורמט JSON
דוגמה חיה: CRUD מלא עם מערך
javascript
העתק קוד
const express = require('express');
const app = express();
app.use(express.json());

let students = [];
let nextId = 1;

// CREATE
app.post('/students', (req, res) => {
    const student = { id: nextId++, ...req.body };
    students.push(student);
    res.status(201).json(student);
});

// READ ALL
app.get('/students', (req, res) => {
    res.json(students);
});

// READ ONE
app.get('/students/:id', (req, res) => {
    const student = students.find(s => s.id === +req.params.id);
    if (!student) return res.status(404).json({ error: 'לא נמצא' });
    res.json(student);
});

// UPDATE
app.put('/students/:id', (req, res) => {
    const student = students.find(s => s.id === +req.params.id);
    if (!student) return res.status(404).json({ error: 'לא נמצא' });
    Object.assign(student, req.body);
    res.json(student);
});

// DELETE
app.delete('/students/:id', (req, res) => {
    const index = students.findIndex(s => s.id === +req.params.id);
    if (index === -1) return res.status(404).json({ error: 'לא נמצא' });
    students.splice(index, 1);
    res.json({ message: 'נמחק' });
});

app.listen(3000);

What is CRUD in Backend Development?
CRUD is an acronym that represents the four fundamental operations a backend application performs on data:

Letter	Operation	HTTP Method	What it does
C	Create	POST	Add a new record to the database
R	Read	GET	Retrieve existing data (all records or one)
U	Update	PUT / PATCH	Modify an existing record
D	Delete	DELETE	Remove a record
Every backend API you build is essentially a CRUD engine. Whether you're managing students, products, users, blog posts — the server's job is always the same: accept requests from the client, perform one of these four operations on the data store, and return a response.

Why Does Almost Every Backend Need CRUD?
1. It Mirrors Real Life
Think about any system you've used: a banking app, an online store, a learning platform. Every action you take is a CRUD operation:

Signing up → Create (new user record)
Viewing your profile → Read
Changing your password → Update
Closing your account → Delete
There is no digital application that doesn't need at least some of these.

2. It Separates Concerns Clearly
CRUD gives you a structured way to organize your code. Each route handles exactly one responsibility. When you open routes/students.js or routes/courses.js (like the files I see in your project — leson1 is already on your GitHub with JavaScript), you know exactly where each operation belongs.

3. REST APIs Are Built on CRUD
The REST architectural style maps directly to CRUD:

sql
העתק קוד
GET    /students     → Read all
GET    /students/1   → Read one
POST   /students     → Create
PUT    /students/1   → Update
DELETE /students/1   → Delete
Once you know this pattern, you can build or consume any REST API.

4. CRUD Is Universal
The pattern doesn't change whether your database is:

A simple JavaScript array in memory
A JSON file
MongoDB, PostgreSQL, or MySQL
The logic stays the same — only the storage layer is swapped.

5. It Enables Dynamic Applications
Your earlier server.js probably returned static responses — the same thing every time. CRUD makes your backend dynamic. Data changes based on real user actions, and every user sees content tailored to them.

In short: CRUD isn't a feature — it's the backbone of backend development. Everything you build from here forward will follow this pattern. Your project leson1 already has routes/students.js and routes/courses.js — those are CRUD routes waiting to be built out.

GET, POST, PUT, DELETE — ארבעת הפעולות של HTTP
אלו ארבע שיטות (methods) של פרוטוקול HTTP. כל אחת מהן אומרת לשרת איזה סוג פעולה הלקוח רוצה לבצע. הן מתאימות בדיוק לפעולות ה-CRUD:

GET — קריאה
מטרה: לקבל נתונים מהשרת. לא משנה כלום, לא יוצר כלום — רק מביא.

מאפיינים:

אפשר לרענן את הדף בלי חשש
אפשר לשמור ב-bookmarks
הנתונים עוברים דרך ה-URL (כפרמטרים)
לא שולחים body בבקשה
דוגמאות:

bash
העתק קוד
GET /students          ← תן לי את כל התלמידים
GET /students/5        ← תן לי תלמיד מספר 5
GET /courses?type=math ← תן לי קורסים מסוג מתמטיקה
בקוד:

javascript
העתק קוד
app.get('/students', (req, res) => {
    res.json(students);  // רק מחזיר נתונים
});
POST — יצירה
מטרה: ליצור משהו חדש בשרת. הנתונים נשלחים ב-body של הבקשה, לא ב-URL.

מאפיינים:

אי אפשר לרענן בלי אזהרה (כי זה יוצר כפילות)
אי אפשר לשמור ב-bookmarks
הנתונים מוסתרים (בתוך ה-body)
כל קריאה יוצרת רשומה חדשה
דוגמאות:

css
העתק קוד
POST /students         ← צור תלמיד חדש
Body: { "name": "יעקב", "grade": 95 }
בקוד:

javascript
העתק קוד
app.post('/students', (req, res) => {
    const newStudent = req.body;   // הנתונים מה-body
    students.push(newStudent);
    res.status(201).json(newStudent);
});
PUT — עדכון (מלא)
מטרה: לעדכן רשומה קיימת. שולחים את כל הנתונים מחדש.

מאפיינים:

דורש ID ב-URL (כדי לדעת את מי לעדכן)
הנתונים החדשים נשלחים ב-body
מחליף את כל הרשומה
ההבדל מ-PATCH:

PUT ← מחליף את כל השדות
PATCH ← משנה רק שדות ספציפיים
דוגמה:

css
העתק קוד
PUT /students/5
Body: { "name": "יעקב", "grade": 100 }   ← כל השדות
בקוד:

javascript
העתק קוד
app.put('/students/:id', (req, res) => {
    const student = students.find(s => s.id === +req.params.id);
    Object.assign(student, req.body);  // מעדכן הכל
    res.json(student);
});
DELETE — מחיקה
מטרה: למחוק רשומה קיימת.

מאפיינים:

דורש ID ב-URL
אין body (בדרך כלל)
מחזיר אישור שהמחיקה בוצעה
דוגמה:

bash
העתק קוד
DELETE /students/5
בקוד:

javascript
העתק קוד
app.delete('/students/:id', (req, res) => {
    const index = students.findIndex(s => s.id === +req.params.id);
    students.splice(index, 1);
    res.json({ message: 'נמחק בהצלחה' });
});
טבלת סיכום
Method	פעולת CRUD	מה זה עושה	Body?	דוגמה
GET	Read	קורא נתונים	❌ לא	GET /students
POST	Create	יוצר חדש	✅ כן	POST /students
PUT	Update	מעדכן קיים	✅ כן	PUT /students/5
DELETE	Delete	מוחק	❌ לא	DELETE /students/5

דוגמאות מעשיות — בלי קוד
GET — חיפוש מוצר בחנות אונליין
נכנסת לאתר של חנות ספרים, מקלידה "מסילת ישרים" בתיבת החיפוש. הדפדפן שולח בקשת GET לשרת: "תביא לי את כל הספרים שהשם שלהם מכיל מסילת ישרים". השרת מחפש במסד הנתונים ומחזיר רשימה של תוצאות. שום דבר לא השתנה בשרת — רק קראת נתונים. אפשר לרענן את הדף מתי שרוצים.

POST — הרשמה לאתר
את ממלאת טופס הרשמה: שם, אימייל, סיסמה. כשלוחצת "הרשמה", הדפדפן שולח בקשת POST עם כל הפרטים שהזנת. השרת מקבל את הנתונים, יוצר רשומת משתמש חדשה במסד הנתונים, ומחזיר אישור. אם תרענני את הדף — תקבלי אזהרה "האם לשלוח שוב?" כי זה ייצור משתמש כפול.

PUT — עדכון פרטי פרופיל
נכנסת להגדרות החשבון שלך, משנה את שם המשתמש ואת תמונת הפרופיל, ולוחצת "שמירה". הדפדפן שולח בקשת PUT: "החלף את כל פרטי המשתמש שלי במה שאני שולחת עכשיו". השרת מקבל, מוצא את הרשומה שלך לפי המזהה, ומחליף את כל השדות.

DELETE — הסרת מוצר מעגלת קניות
באתר קניות, לחצת על האייקון של פח האשפה ליד מוצר בעגלה. הדפדפן שולח בקשת DELETE: "מחק את המוצר הזה מהעגלה שלי". השרת מוצא את הפריט לפי המזהה שלו, מסיר אותו, והעגלה מתעדכנת.

REST API — מדריך למתחילים
קודם כל, מה זה API?
API (איי-פּי-איי) זה פשוט דלת שדרכה שתי תוכנות מדברות זו עם זו.

נגיד שיש לך אפליקציית מזג אוויר בטלפון. האפליקציה עצמה לא יודעת מה יהיה מזג האוויר מחר — היא צריכה לבקש את הנתונים האלה מאיפשהו. היא "דופקת בדלת" של שרת מזג האוויר, והשרת מחזיר לה תשובה. הדלת הזאת — זה ה-API.

REST — דרך מסודרת לבנות את הדלת
REST (רֶסְט) זה אוסף של חוקים פשוטים שאומרים איך לבנות API בצורה שכל אחד יוכל להשתמש בו בקלות. REST ראשי תיבות של REpresentational State Transfer (העברת מצב ייצוגי) — אל תתני לשם להרתיע, הרעיון פשוט.

איך REST API עובד — משל המסעדה
תדמייני שאת במסעדה:

במסעדה	ב-REST API

שלושת העקרונות הפשוטים של REST
1. כל דבר הוא Resource (משאב)

כל דבר במערכת — תלמיד, קורס, מוצר, הזמנה — מקבל כתובת משלו (URL):

bash
העתק קוד
/students        ← אוסף התלמידים
/students/4      ← תלמיד מספר 4
/courses         ← אוסף הקורסים
/courses/7       ← קורס מספר 7
2. הפעולה נקבעת לפי ה-method

אותה כתובת יכולה לעשות דברים שונים, לפי סוג הבקשה:

bash
העתק קוד
GET    /students/4    ← תראה לי את תלמיד 4
PUT    /students/4    ← עדכן את תלמיד 4
DELETE /students/4    ← מחק את תלמיד 4
שלוש בקשות שונות, שלוש פעולות שונות — אותה כתובת.

3. Stateless — בלי זיכרון

כל בקשה לשרת חייבת להכיל את כל המידע שהשרת צריך כדי לענות. השרת לא זוכר מי התקשר אליו לפני דקה. זה כמו להתקשר למוקד שירות — כל פעם את צריכה להזדהות מחדש, גם אם דיברת איתם לפני רגע.

איך נראית תשובה טיפוסית?
בקשת GET ל-/students/4 תחזיר:

json
העתק קוד
{
    "id": 4,
    "name": "יעקב כהן",
    "grade": 92,
    "courses": ["מתמטיקה", "תלמוד"]
}
JSON זה הפורמט המוסכם. כמו שכל המסעדות מגישות אוכל בצלחת — כל ה-APIs מחזירים JSON.

למה REST כל כך נפוץ?
פשוט — כל אחד מבין URL
מוכר — כל הדפדפנים והכלים תומכים ב-HTTP
גמיש — עובד עם כל שפת תכנות, כל מכשיר, כל פלטפורמה
צפוי — ברגע שראית API אחד ב-REST, הבנת את כולם
למעשה, מה שאת בונה עם server.js ו-routes/students.js — את בונה REST API.

למה משתמשים ב-HTTP methods במקום לכתוב את שם הפעולה ב-URL?
זו שאלה מצוינת שמגיעה ללב של REST. בוא נשווה:

הדרך הלא-נכונה: שמות פעולה ב-URL
bash
העתק קוד
POST /createStudent
GET  /getStudent?id=4
POST /updateStudent
POST /deleteStudent?id=4
זה עובד טכנית, אבל זה מבולגן. כל פעולה צריכה URL משלה, ואם יש לך עשרה סוגי נתונים (תלמידים, קורסים, ציונים, מורים...) — נוצר ג'ונגל של כתובות.

הדרך הנכונה: HTTP methods
bash
העתק קוד
POST   /students/4
GET    /students/4
PUT    /students/4
DELETE /students/4
אותו URL — ארבע פעולות שונות. ההבדל הוא ב-method, לא בכתובת.

למה זה יותר טוב? חמש סיבות
1. פשטות — פחות URLs
עם methods, כל משאב צריך רק URL אחד:

bash
העתק קוד
/students          ← כל מה שקשור לתלמידים
/students/4        ← תלמיד ספציפי
/courses           ← כל מה שקשור לקורסים
בלי methods היית צריכה:

bash
העתק קוד
/getAllStudents
/getStudentById
/createStudent
/updateStudent
/deleteStudent
/getAllCourses
/getCourseById
...
זה מתפוצץ מהר.

2. זה הסטנדרט של HTTP
פרוטוקול HTTP נבנה מלכתחילה ככה. שרתי HTTP, דפדפנים, Proxy-ים — כולם יודעים לטפל ב-methods האלה. GET אף פעם לא אמור לשנות נתונים, ו-proxy יכול לנצל את זה ל-caching אוטומטי. PUT ו-DELETE מוגדרים כ-idempotent (להפעיל פעמיים = אותה תוצאה). זה לא סתם מוסכמה — זה בנוי בתשתית של הרשת.

3. כלים אוטומטיים מבינים את זה
Swagger, Postman, curl, ואלפי כלים אחרים מזהים GET, POST, PUT, DELETE ונותנים לך מיד תיעוד אוטומטי, צביעה, והשלמות. אם הפעולה שלך כתובה בתוך ה-URL — הכלים האלה לא מבינים את הכוונה.

4. Security — בקרת גישה פשוטה
הרבה יותר קל לקבוע כלל אבטחה:

bash
העתק קוד
מנהלים → DELETE /students/*
מורים   → PUT /students/*
תלמידים → GET /students/*
אם הפעולה חבויה בתוך URL, צריך לנתח מחרוזות ולנחש.

5. scalability — מוכן לעתיד
נגיד מחר את מוסיפה 20 סוגי משאבים: ציונים, שיעורים, מבחנים, נוכחות, הורים, תשלומים...

ב-HTTP methods, כל אחד מקבל URL אחד. בלי methods — כל אחד צריך 5 URLs. 20 × 5 = 100 כתובות שונות. סיוט לתחזק.

המחשה — משל מפתחות
תדמייני דלת עם חמישה מנעולים, וחמישה מפתחות שונים. זה REST בלי methods — כל פעולה צריכה "מפתח" (URL) משלה.

REST אמיתי: דלת אחת, ויש לך ארבעה מפתחות (GET, POST, PUT, DELETE) שכל אחד מפעיל מנגנון אחר באותה דלת. הרבה יותר אלגנטי.

req.params ו-req.body — ההבדל ומתי משתמשים בכל אחד
req.params — נתונים מה-URL
כשיש לך מזהה בתוך נתיב ה-URL עצמו:

bash
העתק קוד
GET    /books/5
PUT    /books/5
DELETE /books/5
ה-5 שבתוך הכתובת זה req.params.id. השרת קורא אותו מה-URL כדי לדעת על איזה ספר מדובר.

מתי משתמשים: כשרוצים להצביע על רשומה ספציפית — לקרוא אותה, לעדכן אותה, או למחוק אותה.

req.body — נתונים מה-body של הבקשה
כשהלקוח שולח נתונים חדשים לשרת, הם לא מופיעים ב-URL אלא נשלחים בגוף הבקשה (body):

python
העתק קוד
POST   /books    ← שולח { "title": "מסילת ישרים", "author": "רמח"ל" }
PUT    /books/5  ← שולח { "title": "שמירת הלשון", "author": "חפץ חיים" }
הנתונים האלה מגיעים ל-req.body.

מתי משתמשים: כשצריך להעביר מידע ליצירה (POST) או לעדכון (PUT). הנתונים לא גלויים ב-URL, ויכולים להכיל הרבה שדות.

טבלה שמסכמת
req.params	req.body
מאיפה זה בא	מה-URL	מגוף הבקשה
מה זה מכיל	בדרך כלל ID	הנתונים עצמם
איך זה נראה	/books/5 ← ה-5	{ "title": "...", "author": "..." }
מתי	GET, PUT, DELETE לפי ID	POST, PUT
גלוי למשתמש	כן, רואים ב-URL	לא
דוגמה בלי קוד
בקשה: PUT /books/5

req.params.id ← הערך 5 (מאיפה? מה-URL. מה זה אומר? "תעדכן את ספר מספר 5")
req.body ← { "title": "מסילת ישרים", "author": "רמח\"ל" } (מאיפה? מה-body. מה זה אומר? "אלו הנתונים החדשים")
שניהם יחד: "קח את ספר מספר 5, ותחליף את הנתונים שלו באלו שאני שולח עכשיו."

בקשה: POST /books

req.params ← אין. ה-URL לא מכיל ID כי עוד לא נוצר הספר.
req.body ← { "title": "מסילת ישרים", "author": "רמח\"ל" }. "צור ספר חדש עם הנתונים האלה."
בשורה אחת: params אומר את מי, ו-body אומר מה.

אחלה שאלה.

דפדפן — רק חצי עבודה
בדפדפן אפשר רק לקרוא נתונים (GET). את מקלידה כתובת — רואה JSON. זהו.

אבל הפרויקט שלך תומך גם ב:

POST — ליצור קורסים ותלמידים חדשים
PUT — לעדכן קורסים ותלמידים קיימים
DELETE — למחוק
את אלה אי אפשר לעשות מדפדפן. הדפדפן תמיד שולח GET כשלוחצים Enter. אין לו דרך לשלוח body של JSON.

בשביל מה Postman
Postman נותן לך לשלוח כל סוג בקשה — לא רק GET:

פעולה	דפדפן	Postman
GET	✅	✅
POST	❌	✅
PUT	❌	✅
DELETE	❌	✅
לשלוח JSON ב-body	❌	✅
לראות סטטוס (201, 404, 400)	✅	✅
המחשה
תנסי עכשיו בדפדפן לשלוח POST http://localhost:3000/courses — אי אפשר, נכון? אין איך להזין body.

ב-Postman לעומת זאת — את בוחרת POST, כותבת JSON ב-body, לוחצת Send — ונוצר קורס חדש. זה כל ההבדל.

בשורה אחת
דפדפן = לקרוא. Postman = לקרוא, ליצור, לעדכן, ולמחוק.

אז Postman לא מיותר — פשוט עוד לא הגעת לשלב שבו הוא נחוץ. כשתרצי לבדוק POST, PUT, DELETE — תצטרכי אותו.

לגבי Postman שלא עבד
יכול להיות שזו בעיית חיבור לאינטרנט, או שה-Etrog (אתרוג) חוסם את האתר. תנסי לגשת ל-Postman שוב, או לשאול את המורה אם יש כלי אחר שהם משתמשים בו (לפעמים משתמשים ב-Thunder Client, שהוא תוסף ל-VSCode).

מה עוד אפשר לשפר
1. הגנה על DELETE — למנוע מחיקה כפולה
כרגע, אם מוחקים את אותו ID פעמיים — הפעם הראשונה מצליחה, השנייה נותנת 404. זה בסדר, אבל אפשר לשפר:

2. ID לא יכול להיות 0
כבר טיפלנו — if (isNaN(id) || id <= 0). מעולה.

3. מניעת ID כפול ביצירה (POST)
כבר טיפלנו — getNextId() תמיד נותנת ID חדש. אבל מה אם מישהו שולח ID ב-body?

נכון להיום — אם מישהו שולח "id": 1 ב-POST, Express פשוט מתעלם מזה כי אנחנו לא משתמשים ב-req.body.id. אבל נוסיף הגנה מפורשת — נמחק ID אם מישהו שלח אותו. רוצה שאוסיף?

4. Content-Type — לוודא שהבקשה היא JSON
אם מישהו שולח POST עם טקסט רגיל במקום JSON — req.body יהיה ריק. כדאי לבדוק.

ב-server.js נוסיף:

app.use(express.json());
כבר יש לך את זה? אני רואה ב-server.js שאין app.use(express.json()) — וזה קריטי. בלי זה, req.body תמיד ריק.

5. הגבלת אורך טקסט
מה אם מישהו שולח "name": "א" (אות אחת)? או "name": "טקסט באורך 10,000 תווים"? כדאי לבדוק אורך מינימלי ומקסימלי.

6. לוגים — לדעת מה קורה
ב-server.js אפשר להוסיף middleware קטן שמדפיס כל בקשה:

javascript

ככה בטרמינל תראי כל פעם מי דפק על איזו דלת.

כרגע PUT דורש את כל השדות. PATCH מאפשר לשלוח רק את מה שרוצים לשנות. למשל, לעדכן רק סטטוס של תלמיד בלי לשלוח את כל שאר השדות.

תיקון 1: server.js — להוסיף express.json()
תפתחי את server.js.

את רואה את השורות האלה:

javascript
העתק קוד
const express = require('express');
const app = express();
const port = 3000;
מיד אחרי const port = 3000; (לפני const coursesRoutes = require...), תוסיפי שורה ריקה ואת השורה הזו:

javascript
העתק קוד
app.use(express.json());
ככה:

javascript
העתק קוד
const express = require('express');
const app = express();
const port = 3000;

app.use(express.json());

const coursesRoutes = require('./routes/courses');
// ... כל השאר נשאר אותו דבר
למה: בלי השורה הזאת, req.body תמיד יהיה undefined, ו-POST ו-PUT לא יעבדו. express.json() מפענח את ה-JSON שנשלח ב-body והופך אותו לאובייקט.

תיקון 2: server.js — להוסיף לוגים
באותו קובץ server.js, מיד אחרי app.use(express.json()); ולפני app.set('json spaces', 2);, תוסיפי:

javascript
העתק קוד
// לוגים — הדפסת כל בקשה לשרת
app.use((req, res, next) => {
    console.log(`${req.method} ${req.url}`);
    next();
});
התוצאה הסופית של תחילת server.js:

javascript
העתק קוד
const express = require('express');
const app = express();
const port = 3000;

app.use(express.json());

// לוגים — הדפסת כל בקשה לשרת
app.use((req, res, next) => {
    console.log(`${req.method} ${req.url}`);
    next();
});

// הגדרת JSON יפה עם עברית
app.set('json spaces', 2);
// ... כל השאר
מה זה עושה: עכשיו כשתשלחי GET /courses — תראי בטרמינל: GET /courses. ככה תדעי בדיוק מה קורה ומתי.

תיקון 3: routes/courses.js — מניעת ID ב-body
בתוך courses.js, בפונקציית POST, מוסיפים בדיקה קטנה.

מוצאת את השורה:

javascript
העתק קוד
router.post('/', (req, res) => {
    const { name, description, duration, level, price, teacher } = req.body;
מייד אחריה, לפני הוולידציה, תוסיפי:

javascript
העתק קוד
    // מניעת שליחת ID ידני
    if (req.body.id !== undefined) {
        return res.status(400).json({ error: 'אין לשלוח ID ביצירה — הוא נוצר אוטומטית' });
    }
למה: מונע ממישהו לנסות לקבוע ID בעצמו.

תיקון 4: routes/courses.js — הגבלת אורך טקסט
אחרי בדיקת שדות החובה (if (!name || !description...)), תוסיפי:

javascript
העתק קוד
    if (name.length < 2 || name.length > 100) {
        return res.status(400).json({ error: 'שם הקורס חייב להיות בין 2 ל-100 תווים' });
    }
אותו דבר תוסיפי גם ב-PUT, באותו מקום.

תיקון 5: routes/students.js — מניעת ID ב-body
בדיוק אותו דבר. ב-POST, אחרי שליפת השדות מ-body, תוסיפי:

javascript
העתק קוד
    if (req.body.id !== undefined) {
        return res.status(400).json({ error: 'אין לשלוח ID ביצירה — הוא נוצר אוטומטית' });
    }
תיקון 6: routes/students.js — הגבלת אורך שם
אחרי בדיקת שדות החובה:

javascript
העתק קוד
    if (name.length < 2 || name.length > 50) {
        return res.status(400).json({ error: 'שם התלמיד חייב להיות בין 2 ל-50 תווים' });
    }
ב-POST וב-PUT.

סיכום — כל מה שצריך לעשות
#	קובץ	איפה	מה להוסיף

4	routes/courses.js	POST + PUT — אחרי ולידציה	אורך שם 2–100
5	routes/students.js	POST — אחרי שליפת body	מניעת ID
6	routes/students.js	POST + PUT — אחרי ולידציה	אורך שם 2–50
